3. 原来的 P0 风险

   两个通用 JSON 写入口在 rename 失败后直接以 `w` 截断目标；多文件导入只依赖内存补偿；损坏读取之后缺少统一写保护；Safe Recovery 直接 writeFile；备份恢复中断可能留下被移走的正式文件，且回滚错误会被忽略。

4. 现在的原子写入

   在目标所在目录创建 UUID 临时文件，以 `wx` 独占创建，完整写入、fsync、close 后才 rename 到正式路径。集合、文档、安全修复、事务文件和备份归档复用这一底层能力。没有直接截断正式文件的 fallback。

5. rename / replace 失败

   返回带路径和底层 cause 的明确错误；不删目标、不以 `w` 重开目标。临时文件能够清理时清理，清理也失败时返回 AggregateError 并明确保留路径。Windows 遇到文件占用等替换失败直接报错，未引入“先删除旧文件”的替换流程。自动测试验证原文件逐字节保持完整。

6. 损坏数据写保护

   JSON 解析或原有读取校验器失败会登记文件保护状态。普通保存先检查保护状态，再读取并验证现有文件；即使文件尚未加载，非法 JSON 或非法基础结构也不能被空集合覆盖。健康检查使用同一读取层，因此能触发该保护。已登记校验器继续用于保存前验证和恢复验证。

   只有 ENOENT 被视为文件缺失；权限等错误不再伪装成“文件不存在”。合法首次创建可正常执行。保护不会因为普通重读成功而解除；显式恢复校验并替换成功后解除。重启后仍损坏的文件会再次被读取/保存校验阻止。

7. Transactional Import 持久事务

   现有回调仍执行原业务校验与序列化，正式 JSON 写入先被捕获，不逐文件落到业务目标。随后创建 `.data-transactions/tx-UUID` 和 preparing manifest，将原始字节保存为 `.old`、新字节保存为 `.new`，逐文件 fsync 并记录 SHA-256；全部准备成功后才持久化 committing 状态并替换目标。

   原始快照保留到整批提交完成。失败时先验证全部快照、暂存文件以及目标是否匹配旧/新哈希，之后才回滚；原文件恢复原始字节，事务首次创建的文件被撤回。成功写入 committed 状态后，将事务目录改名为 gc 目录再清理，避免清理中断被误认成损坏事务。

   内存 store 自检适配器继续支持原补偿接口；生产 JSON 回调使用磁盘事务。

8. 启动与崩溃恢复

   恢复位于业务加载、IPC 和窗口创建之前。preparing 状态尚未改正式文件，可清理；committing 状态执行经过全量校验的回滚；committed 状态检查最终数据后清理；回滚完成或 gc 状态继续清理。回滚中再次退出也可以重试。

   目标不匹配、快照/日志损坏或缺失、旧版 `.restore-outgoing-*` / `.restore-staging-*` 残留时不猜测覆盖：保留证据，阻止继续读写。启动失败会尝试将完整异常链保存到 userData 下的 `data-safety-startup-error.log`，随后退出；日志保存失败也明确输出错误。没有增加或修改 UI。

   单实例锁避免多个本应用主进程同时管理同一数据目录；同文件普通写入排队，事务/修复期间拒绝外部业务读写。正式提交前规划过程不等同于完整数据库隔离，见剩余风险。

9. Safe Recovery 与备份恢复

   Safe Recovery 已使用 `recoverJsonTextAtomic`，修复内容通过已有校验器后才安全替换。备份恢复继续要求预恢复安全备份，并保留原有“不覆盖备份未包含的数据”及附件集合恢复语义；正式文件、附件新增/替换/删除由磁盘事务统一保护。恢复失败可回滚，回滚失败保留事务证据并阻止继续读写，不吞掉错误。

15. 剩余 P1 / P2 与验证边界

    P1：Node 在 Windows 没有暴露可用的目录 FlushFileBuffers 接口。本实现对文件执行 fsync，其他支持的平台还对目录执行 fsync；不能承诺磁盘控制器、电源故障或存储硬件违约下的绝对持久性。完成的是实际进程中断/重启测试，没有进行物理断电试验。缺失/损坏日志会阻断启动并保留现状。

    P1：JSON 方案不是完整数据库事务；业务“读取—规划”到开始事务之间的陈旧结果冲突、外部程序同时修改文件，以及普通手动备份的跨文件一致性仍属于后续审计范围。本次没有改变业务规则来解决这些问题。

    P1：旧版恢复残留或哈希无法判定的事务需要人工处理；自动猜测恢复被明确禁止。磁盘空间耗尽或权限问题导致回滚不能完成时，应用保留快照并停止继续写入。

    P2：失败启动通过日志诊断，尚无新的恢复 UI；崩溃时单文件写入可能留下未引用的 `.tmp`，正式文件仍由替换机制保护，未增加自动批量删除未知临时文件的功能。事务需要旧/新副本的临时磁盘空间；成功后自动清理，不积累事务备份。
